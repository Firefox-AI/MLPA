Guest

Guest tokens for Smart Window users without an account.

Flow

  1. GET /verify/v1/guest with Accept: application/json returns a token. If Fastly answers with a challenge instead, open the same URL in a browser tab and read the token from the /verify/v1/guest/success#access_token=... redirect.
  2. Send the token as Authorization: Bearer <token> to /v1/chat/completions or /v1/search, with the usual service-type (e.g. ai). MLPA maps it to the guest pool (ai → ai-guest) with its own budget.
  3. When the token expires, chat answers 401. Call POST /verify/v1/guest/refresh with the expired token and retry with the new one. Refresh is a plain JSON call with no Fastly challenge or browser tab, and keeps the guest id (sub), so budget and cap slot stay.
  4. Refresh answers 401 when the token is too old. Go back to step 1, this gives a new guest id.

Lifetimes (defaults, each env sets its own in infra)

Setting Default Meaning
MLPA_GUEST_TOKEN_TTL_SECONDS 604800 (7 days) Token valid for chat until exp.
MLPA_GUEST_REFRESH_IDLE_SECONDS 2592000 (30 days) Token (expired or not) refreshes while its iat is younger than this. Each refresh restarts the clock, so an active guest never has to re-issue.

Read exp from the JWT to refresh ahead of time, or just refresh on 401.

Errors

Status Body When Client action
401 {"detail": "Invalid guest token"} Chat: token expired or bad signature. Refresh: not a guest token or bad signature. Chat: refresh. Refresh: issue a new token.
401 {"detail": "Guest token too old to refresh"} Refresh: iat older than the idle timeout. Issue a new token.
401 {"detail": "Guest access is disabled"} Chat while the kill switch is off. Sign in with FxA.
404 {"detail": "Guest tokens are disabled"} Issue or refresh while the kill switch (MLPA_GUEST_ENABLED) is off. Sign in with FxA.
403 {"detail": {"error": 12}} Guest cap (MLPA_MAX_GUESTS) is full and this guest has no slot: new guest at chat, or refresh after its slot was cleaned up. Sign in with FxA.
400 {"detail": "service-type 'x' is not available for guests"} Service type has no -guest pool. Don't call it as a guest.
429 {"detail": {"error": 1}} This guest's own daily budget is used up. Wait Retry-After, or sign in.
429 {"detail": {"error": 11}} Shared budget for all guests is used up. Wait Retry-After, or sign in.
503 {"detail": {"error": "Guest access is not configured."}} Guest virtual key missing on the server. Server config issue.

With "stream": true the budget errors arrive inside the stream as data: {"error": N}.

Guest cap slots are freed by infra cleanup after a token TTL without activity. Refresh keeps the slot active, or claims a new one if it was freed.

Get Guest Token

Issue a guest access token.

Fetch with Accept: application/json to get the token in the body. If Fastly answers with a challenge instead, open this URL in a browser tab and pass it. MLPA then redirects to /verify/v1/guest/success with the token in the URL fragment. Watch the tab URL for that path, read the fragment, then close the tab.

The token is valid for MLPA_GUEST_TOKEN_TTL_SECONDS (default 7 days, set per env in infra), see the JWT exp claim. After that, refresh it with POST /verify/v1/guest/refresh instead of fetching a new one, so the guest keeps its id and budget.

Refresh Guest Token

Refresh a guest token, keeping the guest id (sub), so its budget and guest cap slot stay the same.

Send the current token as Authorization: Bearer ..., expired or not. It refreshes while its iat is younger than MLPA_GUEST_REFRESH_IDLE_SECONDS (default 30 days, set per env in infra). The new token gets a fresh iat and exp (MLPA_GUEST_TOKEN_TTL_SECONDS, default 7 days), so each refresh restarts the idle clock.

Call it when chat answers 401 for a guest token, then retry the request once with the new token. It's a plain JSON call with no Fastly challenge, so there is no browser tab flow. On 401 from refresh, fall back to GET /verify/v1/guest. Errors are listed in the Guest section above.

Search

Web search proxied to Exa via LiteLLM. Authorize the same way as /v1/chat/completions.

Headers:

  • Authorization (required): Bearer token — FxA OAuth token, Play Integrity MLPA token, App Attest JWT, or guest token (see the Guest section).
  • service-type: search by default; use search-dev for experiments. Search has its own budget pool and no purpose header.
  • x-dev-authorization (required for search-dev): Experimentation token; also requires FxA in Authorization.

Required body fields: query (string) and max_results (integer, 1-10).

Optional Exa filters:

  • includeDomains (array of strings): Restrict results to the specified domains.
  • excludeDomains (array of strings): Exclude results from the specified domains.
  • startPublishedDate (string): Return results published after this ISO 8601 timestamp.
  • category (string): Focus the search on a category, such as news.

Send filters at the top level of the JSON body. Omitted or null filters are not sent to Exa.

Example:

{
  "query": "Firefox browser news",
  "max_results": 5,
  "includeDomains": ["mozilla.org"],
  "excludeDomains": ["example.org"],
  "startPublishedDate": "2026-01-01T00:00:00Z",
  "category": "news"
}
